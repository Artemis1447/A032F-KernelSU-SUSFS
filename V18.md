# Galaxy A03 Core SM-A032F — V18 stock-derived

This branch builds the arm64 kernel for the `a3core` LineageOS 21 / Android 14 **ARM32** installation. The comparison is against the V17 SukiSU-Ultra/SUSFS release. `Image` is the raw kernel, **not** a complete Android Boot image.

## Provenance and changes

* Build recipe: [V17 tag `5fbb027`](https://github.com/Artemis1447/A032F-KernelSU-SUSFS/tree/a3core-v17-sukisu-susfs-20261124). The V17 release asset actually came from run `45299270122`, commit `d57bce53`; only the README changed between that commit and the tag. V17 `Image` SHA-256: `9b2f68f6b37a0031ffc7cec89c5239342328991e93c2d522019c9db498af98fe`.
* Kernel: `IverCoder/android_kernel_samsung_a3core` at `81da2968a777556d20847e30b618658905af67a3`; the Samsung stock source merge is `3b5c5894347` (A032FXXS6CXE2). V17's integration steps install SukiSU-Ultra `4bec532dd447e2852aa8932afa768255350c103a` and SUSFS `77905b5a071e6f3669e3b1814cea30147c0801da` with V17's compatibility patches.
* The V17 profile named a kernel commit, but its config reader did not export that key and its fetcher used the branch tip. V18 checks out/verifies the recorded kernel and SUSFS revisions. Files: `config/a3core-a032f-v18-stock.env`, `scripts/{config,lib,source,patches}.sh`. `scripts/package.sh` includes the integrated source in this profile's ABI artifact. No device behavior is attributed to those build-system changes. The build needs the pinned objects to remain fetchable.

| Kernel commit | Changed file | Reason and expected effect | Possible regression |
|---|---|---|---|
| `391183c8f99` | `drivers/staging/android/ion/ion_system_heap.c` | Remove unconditional per-buffer clock reads, order counting and printk. A V17 capture contains 757 lines in 206 s; 145 are 4,608,000-byte display buffers. Reduces graphics-path work and log traffic. | Removes these per-allocation diagnostics. Heap selection, scatterlists, frees and failure paths are retained. |
| `2fee8599b23` | `drivers/block/zram/zram_drv.c` | Backport [upstream `90f82cbfe502`](https://github.com/torvalds/linux/commit/90f82cbfe502e96e602614ebbaf7725470c5208a): compare the first and last word before walking the middle of a swap-out page. All words are still checked before declaring a page uniform. | An extra cache-line access for some early mismatches. Helps writes with a uniform prefix; it does not make swap-in decompression faster. No format or memory-limit change. |
| `fcbcdd8b42f` | `kernel/sched/cpufreq_schedutil.c` | The vendor governor expired I/O boost but continued counting a stale idle CPU's utilization/deadline vote. After a task leaves a core, omit that vote once it is older than one tick **and** the core is idle. Do this in both the scheduler decision and SPRD's deferred driver worker, using the triggering scheduler timestamp. | A cluster may downscale sooner between intermittent bursts; the next runnable task may need to ramp again. Busy/tickless CPUs, fresh boosts and active deadline votes still count. No change to placement masks or CPUFreq limits. |

The three exported kernel commits live in [`patches/v18/`](patches/v18). Apply them with `git am` to the pinned kernel to edit the source, or use the build profile below to reproduce the integrated kernel. Do not apply them twice. On Windows the kernel checkout is sparse because upstream tracks case-colliding paths; the full build and the `v18-source.tar.gz` source archive use a case-sensitive Linux filesystem.

## Platform audit and launch diagnosis

| Area | Source and device evidence | V18 decision |
|---|---|---|
| CPU and migration | `arch/arm64/boot/dts/sprd/sc9863a.dtsi`, `drivers/cpufreq/sprd-cpufreqhw.c`, `kernel/sched/{fair,tune,cpufreq_schedutil}.c`. Eight A55s, two shared policies. CPUs 0–3: 768/884/1000/1100/1200 MHz; 4–7: 768/1050/1225/1400/1500/1600 MHz. WALT CPU/task utilization enabled; MC/DIE domains; top-app CPUs 0–7, boost 30; background CPUs 0–3. Schedutil up/down limits 500/1000 µs; frequency margins 50/30. | Fix stale votes. Retain energy-aware wake placement, vendor rate limits, and launch PowerHAL. The archived settled V17 medians were 1,028 ms with schedutil vs 1,024 ms at forced maximum CPU frequency. |
| Idle, workqueues, thermal | Tickless idle, HZ=250, PSCI and `menu`; WFI 1 µs, `core_pd` DT entry/exit 1000/500 µs, reported latency 1500 µs, minimum residency 2500 µs. Power-efficient workqueues enabled. `drivers/thermal/{power_allocator,sprd_cpu_cooling}.c`; live `power_allocator`, CPU trips 70/85/110 °C. | Preserve deep idle, workqueue affinity and thermal limits. No evidence that disabling idle or raising trip points would improve the foreground workload. |
| Memory | 1,890,924 KiB visible; PSI, memcg swap, zsmalloc. Active ZRAM 2.5 GiB, `lzo [lzo-rle] lz4 deflate`, no backing device on the tested boot; swappiness 140, page-cluster 0. `drivers/block/zram/zram_drv.c`, `mm/{vmscan,swap_state}.c`. | Optimize the identical-page scan; keep the active compressor, swap and reclaim policy. Test LZ4 and LZO-RLE on a disposable secondary device so the ROM's swap isn't reset or reformatted. |
| Storage | eMMC is on the legacy queue: `[noop] cfq`, 128 requests, 512 KiB read-ahead. DM queues have no scheduler and 128 KiB read-ahead; userdata is F2FS. The CFQ defconfig default and the schedulers on MQ loop devices do not describe the live eMMC queue. Vendor init also writes read-ahead values. | Keep runtime queue choices. `scripts/check-a3core-device.sh` measures direct eMMC reads; it does not write to flash blocks or change read-ahead. |
| Rendering | `arch/arm64/boot/dts/sprd/sharkl3.dtsi`: `sprd,rogue`, 256/384/550 MHz. The live driver is PowerVR `pvrsrvkm`, **not Mali**. Devfreq: `simple_ondemand`, 50 ms poll; separate DDR `sprd-governor`. `m168-overlay-pvt.dts` covers the board. | Remove ION logging in the actual allocation path. Preserve vendor GPU module, OPP table, DTB/DTBO, PowerHAL and thermal cooling. Verify the 267 stock module CRCs at build time. |
| Android integrations | V17 arm64+COMPAT, Binder/binderfs, module versioning, enforcing SELinux, SukiSU-Ultra and SUSFS v1.5.5. Seven modules on the current device; older recordings had six. | Retain V17's config and hooks. Test a real `su` grant, the existing SUSFS extension query, enumerated modules and driver initialization. A successful query is not a test of every SUSFS feature. |

**Why the 743–800 ms best is hard to reproduce:** the workspace has no matched series or trace for that best. On V17 alone, `bench_E0_confirm.txt` gives 1,028 ms (4 process-cold launches), vs 1,254 ms in `bench_E16_final_stock.txt` (12 after reboot; +17,915 swap-in pages and +18,458 major faults across the window). This shows sensitivity to boot/cache/background state; aggregate counters do not attribute each fault to Settings. In `gap_analysis.txt` the app logged preferences complete at 00:39:47.396; Android recorded first display at .956. Gralloc buffer calls appear late in that **560 ms** interval, taking roughly 1–2 ms each in that trace. In the separate V17 dmesg, measured page-gathering for full-screen buffers had median **54 µs**, maximum **6.569 ms**; that timer excludes printk and subsequent scatterlist setup. These observations neither time the whole render pipeline nor assign the old-to-new regression to a single kernel commit.

Two limits on interpreting the older experiments: in `bench_E10_E11.txt` the requested GPU/DDR pin was followed by a 256 MHz GPU readback and 933 DDR readback; this did not demonstrate a sustained 550 MHz GPU during launch. Aggressive scheduler granularity/migration settings in the second half gave a median of 1,096 ms. The reported swap-reset experiments also changed cache and background state. None is a matched V17/V18 measurement.

## Build and verify

From a clone of **this build recipe**, with GitHub CLI authenticated for the repository's Actions:

```sh
git switch v18-stock-derived
gh workflow run build-kernel.yml --ref v18-stock-derived \
  -f config=config/a3core-a032f-v18-stock.env -f publish_release=false
# Use the run ID printed by the dispatch (this build: 45909569877).
gh run watch "$RUN_ID" --exit-status
gh run download "$RUN_ID" -D artifacts
```

The existing Ubuntu workflow uses Android Clang **11.0.1 r383902**, `ld.lld`, AOSP GCC 4.9 arm64/arm32 binutils (`android-12.1.0_r27`), `ARCH=arm64`, `a3core_eur_open_defconfig`, and the `sharkl3` BSP flags. It links `Image`, checks the selected SUSFS subset and stock GPU CRCs, and packages the result. The `pvrsrvkm-ABI-*` artifact includes `Module.symvers`, `kernel.config`, the CRC report, and `v18-source.tar.gz` (actual integrated tree, including KSU and the effective board defconfig). No release publication is required. The V17 tag and its release remain available independently.

For a full offline cross-check, run `python scripts/verify-a3core-v18.py artifacts v17.config verification.json` with Python 3.9+ and the original V17 built config (also in the V17 run's GPU ABI artifact). It compares the linked IKCONFIG to CI and V17, verifies the integrated source blobs against the patches, and independently reproduces the vendor CRC report. To check just the GPU ABI:

```sh
python3 scripts/verify-pvrsrvkm-abi.py --expected config/pvrsrvkm-a032f-stock-crcs.json \
  --symvers artifacts/pvrsrvkm-ABI-*/Module.symvers --report gpu-crcs.tsv
```

### Rebuild from the delivered full kernel source on Linux

The `v18-source.tar.gz` archive already contains the integrated sources and modified board defconfig. Extract it on a case-sensitive filesystem. Use the same Clang and GCC/binutils directories installed by `scripts/toolchain.sh` in the CI workspace. For example, with `TC` pointing at that toolchain workspace (verify `clang --version` reports r383902):

```bash
mkdir kernel-v18 && tar -xzf v18-source.tar.gz -C kernel-v18
cd kernel-v18
export PATH="$TC/clang/bin:$PATH"
args=(O=out ARCH=arm64 CC=clang LD=ld.lld CLANG_TRIPLE=aarch64-linux-gnu-
      CROSS_COMPILE="$TC/gcc-64/bin/aarch64-linux-android-"
      CROSS_COMPILE_ARM32="$TC/gcc-32/bin/arm-linux-androideabi-"
      BSP_BUILD_FAMILY=sharkl3 BSP_BUILD_DT_OVERLAY=y BSP_BUILD_ANDROID_OS=y HOSTLOADLIBES_dtc=-lyaml)
make "${args[@]}" a3core_eur_open_defconfig
make -j"$(nproc)" "${args[@]}"
```

The workflow is the reference for release metadata: KSU version discovery can depend on Git metadata, and the source archive omits `.git`. Use the pinned recipe checkout when matching the release version labels. The linked artifact is `out/arch/arm64/boot/Image`. Apply the same config and stock CRC checks before packaging another build.

## Install and roll back (single-slot SM-A032F, TWRP)

Use the exact boot backup of **your** current unlocked V17 installation. The ramdisk in the test phone's live boot differs from `dfe_boot.img` despite their kernels being identical. A raw `Image` is not flashable as Boot. Recovery is a separate partition on this model.

1. Reboot to the working TWRP (`adb -s SERIAL reboot recovery`). Back up **Boot** off-device and check its SHA-256 against `adb -s SERIAL shell sha256sum /dev/block/by-name/boot`. In a binary-safe shell on Linux, `adb -s SERIAL exec-out cat /dev/block/by-name/boot > boot-v17-device.img` does this. On Windows use `cmd.exe` redirection or Python binary I/O; do not pipe partition bytes through Windows PowerShell text redirection. Keep this backup and its hash for recovery.
2. On the host, `python scripts/repack-a3core-v18.py boot-v17-device.img Image boot-v18-device.img`. Compare the raw kernel and candidate hashes with the delivery manifest if using this build and this handset. The repacker preserves the ramdisk, DTB, cmdline and Samsung trailer, regenerates the legacy boot ID, and preserves the embedded vendor vbmeta bytes. The OEM descriptor did not match this unlocked handset's V17 payload either; the result is **not an OEM-signed image for locked bootloaders**.
3. From the recipe checkout and with the phone in TWRP, run the following. Replace `SERIAL` and the two digest placeholders with the values you have independently checked. The helper verifies the handset, partition mapping/size, original hash, staged bytes and complete readback. It does not reboot:

   ```sh
   python scripts/install-a3core-boot.py --serial SERIAL \
     --expect-current V17_BOOT_SHA256 --target-sha256 V18_BOOT_SHA256 boot-v18-device.img
   adb -s SERIAL reboot
   ```

4. After Android reports `sys.boot_completed=1`, check `uname -r`, `getenforce`, `/proc/modules`, and `adb -s SERIAL shell 'su -c "/data/adb/ksud extension get susfs"'`. `scripts/check-a3core-device.sh` (pipe via `adb -s SERIAL shell -T su -c sh`) checks the driver and root service and runs bounded I/O and compression tests. It uses the installed KSU BusyBox, creates an 8 MiB temporary input and a separate ZRAM device, verifies both codec readbacks, then removes them. It also records HWUI frame statistics for eight down/up scroll pairs in Settings. For paired runs, measure launches before running these subsystem checks.
5. **Rollback:** enter TWRP by ADB or, if Android won't start, with USB connected and **Volume Up + Power** at restart (Volume Down + Power forces a restart; switch to Volume Up at the black screen). Run the same installer with `--expect-current V18_BOOT_SHA256 --target-sha256 V17_BOOT_SHA256 boot-v17-device.img`. Confirm full readback and reboot. For an interrupted write, first read the actual partial Boot hash in TWRP and use it as `--expect-current` after confirming the device and your backup. A TWRP Boot backup from step 1 can also be restored through TWRP's Restore menu. No data wipe, recovery/DTBO write or vbmeta change is part of this procedure.

## Comparable Settings measurements

Use the same ROM, module set, screen/animation settings, charging state and USB connection. Reboot, leave the launcher foreground and the current user unlocked, and run this before 240 s uptime on each kernel:

```sh
python scripts/bench-a3core.py --serial SERIAL --kernel v17 --at-uptime 240 --out v17-matched.json
# Repeat after installing V18, using --kernel v18 and a new output path.
```

The tool waits for the same boot age, runs two warm-ups followed by 12 valid process-cold `am start -W` Settings launches, and reports the median `TotalTime`. It records raw launch times, temperatures, policy/Devfreq state, module state, memory pressure and disk counters; warm attempts are recorded separately. No cache drops, swap resets, forced clocks, disabled modules or dex recompilation are part of this protocol. Inspect the temperatures, available memory and pressure counters before interpreting small differences.

This evaluation also repeats the launch series at 420 s on the same boot, then runs the storage/ZRAM/scroll checks followed by a bounded 60 s CPU load. Four ordinary checksum workers read the cached ROM framework file; CPU temperature and both policy frequencies are sampled every five seconds. The test stops at the first configured CPU thermal trip. This checks short-term behavior under load, not sustained gaming thermals or battery life.
